# Google Slides と Slipper の両側から資料を育てる

2026-09-27

## 目標と判断

ユーザーが目指すのは、思いつく・作る・見比べる・直す・仕上げるまでを支えるスライドエディターである。ユーザーが説明したペルソナBは、他の人との共同編集を必要とする。Google Slidesでの編集を残し、Slipperを使わない仲間と同じ資料を編集できることを必須条件とする。ペルソナ文書そのものを今回取得できたわけではなく、この会話で示された条件を根拠にしている。

共有資料はGoogle Slidesに持つ。Slipperは同じ要素を直接編集し、AIへの指示や複数候補の比較、素材・部品・配色を試す操作を加える。ローカルの試行錯誤は下書きとして保ち、利用者が選んだ変更を共有資料へ反映する。

利用者の操作場所を一方へ限定しない。Googleで更新した文章をSlipperで整え、Slipperで編集した文字や図をGoogleでさらに直せることが基準になる。

## 今回作った一連の操作

1. Google Slidesでページを開くと、Slipperの「編集する」で同じページを読み込む。
2. 画像上または一覧から要素を選ぶ。文字を直し、対応する要素の配置や大きさを変える。複数選択して整列・等間隔配置もできる。
3. 選択した文章について「条件を残して短く」「結論を先に」などを頼み、AIの候補を比べる。採用した候補は下書きへ入る。
4. 変更前後を確認して「同じページに反映」する。既存要素への更新であり、共有資料を複製したりページを画像化したりしない。
5. 相手が同じ箇所を変えていた場合は、双方の内容を比較して選ぶ。別の箇所への変更は維持する。
6. Google側で続けて編集できる。Slipperの下書きはローカルへ保存し、再起動後も元の比較基準とともに復元する。

## 共同編集の扱い

`LiveEditor`サービスはGoogleから読んだページと版を保持する。反映の直前に読み直し、編集開始時・現在・下書きを比較する。文章と配置は独立した変更として扱う。同じ文章内の別々の編集を自動統合することはせず、文章単位で比較する。

競合があればバッチ全体を止める。利用者が各競合の残す側を選ぶと、新しい基準で下書きを作る。共有資料への反映はその後の操作になる。削除された要素は再作成せず、下書きを比較画面に残す。

競合がなければ、最新の `revisionId` を `writeControl.requiredRevisionId` に入れてGoogleへ送る。読み直しと書き込みの間に変更された場合も、古い版での上書きを防ぐ。失敗時に版の指定を外して再送しない。応答を失った可能性があるときは、最新を確認して再比較する。

- [Google Slides: batchUpdate / WriteControl](https://developers.google.com/workspace/slides/api/reference/rest/v1/presentations/batchUpdate)
- [Google Slides: 要素の変形と文字の編集](https://developers.google.com/workspace/slides/api/reference/rest/v1/presentations/request)

文字は共通の前後部分を残し、変更範囲だけを削除・挿入する。UTF-16のインデックスを使い、絵文字のサロゲートペアを分断しない。配置は元のアフィン変換を使い、回転・反転を保って更新する。

取り消しも通常の変更と同じ比較を行う。反映後に同じ箇所が変更されていれば止める。取り消しで別の人の作業を巻き戻さない。

## AIの文章候補

選択文章・ページの文章・資料の聞き手と目的を渡し、2〜3案を作る。AIに共有資料を書き換えるツールは渡さない。候補は数値の保持を検査した後、別の呼び出しで元文章と条件・意味・順序を照合する。合格した候補だけを表示する。意味の保持を保証する仕組みではない。

実生成で「試行→効果の確認→採否判断」が「効果の確認→試行→採否判断」に読める候補が出た。数字の一致検査では通るため、独立した照合を追加した。同じ候補を固定して実AIの検証へ再投入し、問題の候補が除外され、元の順序を保つ候補は残ることを確認した。固定例は `test/fixtures/text-sequence.json`。

## 確認した範囲

- 自動テスト：文章と配置の独立した変更、文章の競合、削除、回転変更、回転を保った配置更新、版不一致、取り消しの競合、書き込み成功後の読み込み失敗、絵文字、等間隔配置、下書きの再起動復元、AIの数値検査と候補の照合。
- 実Google API：専用資料で他の編集者の変更をAPIから模擬し、既存要素のIDを保った更新・取り消し・競合停止・古い版の拒否を確認。
- 実Electron画面：同じReactコンポーネントとpreloadを使い、要素選択→文章編集→競合比較→Google側の文章を残す→再編集→反映を操作。560px幅で横はみ出しがないことを確認し、画像を目視した。
- 実Claude Code：候補の生成と下書きへの取り込みを確認。共有資料には自動反映されないことを確認。

複数の人がブラウザで同時に操作した利用テストではない。Googleの編集画面との更新の遅れ、大規模な資料での負荷、複雑な書式の往復は追加検証が必要。

検証用資料：[Slipper QA — collaborative editing](https://docs.google.com/presentation/d/1GWlQYNmZoNuUvgpe0x-i8j9PiuMQWLDu_TriyRtQliI/edit)

```sh
# 専用資料を1つ作成して、実Google APIとElectron画面を確認する
SLIPPER_EVAL_GOOGLE=1 node scripts/evaluate-live-edit.mjs
# 実AIによる文章候補の生成・照合まで含める（Claude Codeの利用量を消費）
SLIPPER_EVAL_GOOGLE=1 SLIPPER_EVAL_LIVE=1 node scripts/evaluate-live-edit.mjs
# 固定した意味の誤りを、実AIの照合へ再投入する。Googleへの書き込みはしない
SLIPPER_EVAL_REPLAY_TEXT=test/fixtures/text-sequence.json node scripts/evaluate-live-edit.mjs
```

出力は `/tmp/slipper-live-edit-eval`。専用資料を再利用する場合は `SLIPPER_LIVE_EDIT_DECK` にそのIDを渡す。タイトルがこの検証用の接頭辞で始まる資料に限り、`live_page`を再作成する。

## 次に広げる体験

1. **変更後の見た目までその場で比べる**：今の画像はGoogle側の表示。配置案は点線、文章は差分で確認する。ローカル下書きの完成描画とGoogleの結果を近づけることが次の大きな課題。
2. **部品・配色で表現を切り替える**：内容と条件を維持しながら、比較・手順・関係図などを切り替える。編集可能なGoogleの文字・図形で組み立て、共同編集者が続けて触れるようにする。
3. **選択範囲へのAI編集を広げる**：文章だけから、複数要素の図解やページ構成へ。変更対象と維持する条件を表示し、今の比較・下書き・反映の流れへつなぐ。
4. **資料全体を仕上げる**：構成案から必要なページを作り、色・書体・余白を揃え、発表としての流れを確認する。

グループ内部、表セル、マスター由来の配置、詳細な書式の編集は現段階ではGoogle側で行う。削除した文字の細かな書式まで取り消しで復元するものではない。APIからは資料全体のページデータを取得しているため、大規模な資料の更新取得は最適化の余地がある。
